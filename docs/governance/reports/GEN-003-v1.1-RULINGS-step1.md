## F4 — the second empty oracle. Do not merge the tsConfig fix by itself.

After the fix and a successful build, depcruise still cannot resolve `@pemo/*`: 14 `couldNotResolve` specifiers, 0 cross-module edges. Every module-to-module import in this codebase is a bare `@pemo/*` specifier, so **the exact edges `no-module-to-module` and `no-simulator-in-runtime` exist to catch are the edges the tool cannot see.**

v1.0's zero came from a tool that could not start — visibly broken. This zero would come from a tool that starts, runs, reports clean, and is blind to everything that matters. **It looks like a result, and that makes it worse.** A dead oracle is caught by anyone; a confident blind one is caught by no one.

Rulings:
- **The tsConfig fix is not committed on its own.** A tool that resolves its config but not its module graph is a clean-and-blind oracle, and merging it would plant exactly the false green the battery exists to prevent. The `@pemo/*` resolution and the tsConfig fix land together or not at all.
- **Propose the resolver fix at the next step; I am not asserting it.** The likely shape is the tsconfig `paths` reaching depcruise's resolver (via its `tsConfig`/enhanced-resolve options), but I have not run it and a fix asserted from here is the state-I-have-not-established failure.
- **Done-when for the resolver is a caught edge, not a clean run.** Introduce a genuine cross-module `@pemo/*` import; show it resolves to an edge AND `no-module-to-module` (fixed per the earlier F2, `pathNot: '^modules/$1/'`) fires on it; remove it and show the count drops. Prove the tool can SEE a real edge before any zero it reports is trusted. Until that caught edge exists, the graph is presumed blind and every zero from it stays void.

## F5 — split the done-when. The DROP SCHEMA invariant leaves GEN-003, but it does not leave the board.

You are right that the PID conflated two different couplings under one tool:

1. **Import coupling** — module-to-module, and simulator-reaching-runtime. These are import questions. They belong to depcruise, pending F4. `no-simulator-in-runtime`: nothing outside `dev-simulator/` references it by path (grep empty, consistent with it being its own entry point), so this one is answerable by the graph once the graph can see.

2. **Data / schema coupling** — the `DROP SCHEMA` → 33-fail evidence. `screen-content.ts` is ordinary code importing `@pemo/platform` and querying a schema. **No import graph can see a data dependency at any configuration.** Fixing depcruise will not reproduce that red, and a clean `no-simulator-in-runtime` does not contradict it — they are compatible facts about different couplings.

Rulings:
- **GEN-003 keeps only the import invariants.** Its done-when is the two caught reds: a real cross-module import caught by `no-module-to-module`, and a simulator import into a runtime path caught by `no-simulator-in-runtime`. Both via depcruise, both after F4.
- **The `DROP SCHEMA` → 33 schema-coupling invariant is removed from GEN-003 and spun out to a new PID** — a runtime or schema-level check, not an import-graph one. It is a real invariant and it must NOT silently drop off the board because the tool pointed at it cannot see it. It is now **owed**: allocate its number from the directory when issued, do not carry one forward in prose. This is recorded here so the invariant survives the tool change that orphaned it.
- The lesson, not written as a new principle because the control is the caught-edge done-when, not a rulebook line: an invariant does not become satisfied because the tool assigned to it went blind. When a tool is found unable to see a coupling, the coupling is reassigned, not closed.

## F1 scrub — both conflicts resolve on one decision about the guard's domain

- **The closed `DOC-002-step2.md` is not edited.** Rule 7 holds. A report in `reports/` is a provenance artifact, not an execution surface — nobody runs a markdown report — so the hazard the scrub targets (a command being executed) does not live there. Leaving it is correct, not a gap.
- **The grep-guard matches invocations, not mentions, by scoping to execution surfaces only** — shell scripts, `package.json` scripts, CI YAML, `Makefile`, `bin/` — and never `*.md`. That single scoping resolves both conflicts at once: the closed report's mention is markdown and is not matched (so no rule-7 violation is needed), and GEN-003 v1.1's own ban text and this ruling are markdown and are not matched (so the guard does not flag its own definition). Propose the exact matcher at the next step; the domain is execution surfaces, and a guard that flags its own ban is the self-matching defect it must be built to avoid.
