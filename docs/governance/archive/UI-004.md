**The twist rule — this line's hard constraint (the seam between tiers):**
- The **front-end owns presentation only** — layout, formatting, i18n, non-security ordering, composing already-authorized fields into a widget shape.
- The **app-server owns authorization and derivation** — what data, whose data, filtered in-query, and every safety-relevant computed value. A design must **not** assume the client filters or derives anything the server should. If a screen needs data it does not have, that is a **contract field request** — recorded, never a client-side computation.

**Designing against a partially-accepted design system.** Only §3 / §3.1 (severity) and part of §4 (typography) are Product-Owner-Accepted; §7 (navigation), §9 (management-web visual rules) and §18 (state coverage) are **Proposed baseline**. **Design against the Proposed sections, with their status disclosed per section** — a design is how a proposal gets tested before acceptance. What is forbidden is designing against them *silently*, which is how "Proposed" becomes "Accepted" with nobody deciding. Anything the deck **depends on** from a Proposed section is listed as a decision the Product Owner still owes.

## Done when

- Every screen has an artboard for **every state, discriminated** — the design system §18 baseline: **loading, empty, partial, error, offline, stale, no-permission, session-expired**, plus **long EN and Traditional-Chinese content** checked against *every* state (a rendering property, not a ninth state). **Home Safety additionally carries §18's ten screen-specific states.** A state that does not apply is recorded as N/A **with its reason**, never silently dropped.
- **Screen states and content states are not confused.** A screen state is about the viewer's own access or fetch. A fact about an entity the screen displays (a lapsed caregiver permission, an unmapped unit) is **content**, rendered per the Properties pilot's pattern — not a state of the screen.
- **Deferred writes render as absent**, not as dead or disabled controls. A control the viewer could reasonably expect but does not hold renders **present, unavailable, with the reason**.
- Each artboard needing data beyond what the contract exposes carries a **CONTRACT FIELD REQUEST** (screen → field → why), delivered **once, whole**, at the end of Step 2.
- Divergences from the design system are **recorded beside the file**, not silently repainted.
