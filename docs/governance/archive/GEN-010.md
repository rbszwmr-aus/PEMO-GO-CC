# GEN-010 — The least-privilege role model (GEN-009 precursor)

Implements `rewrite/decisions/least-privilege-db-roles.md`. **Unblocks GEN-009 and all 27 scope-only writes** — nothing is immutable to the app until this lands, because a superuser bypasses every table permission.

Greenfield: the repository provisions no deployment and refuses to run outside `development` (`config.ts:76-86`), so there is no live estate to migrate. This is the cheapest this model will ever be — no cutover, no live-data risk.

## What to build

- **`pemo_owner`** (confirm the name against existing conventions at Step 1) owns the schemas and tables; migrations run as it.
- **`pemo_app`** is the non-superuser runtime role, granted the DML each of the 42 tables legitimately needs — `SELECT`+`INSERT` everywhere, `UPDATE`/`DELETE` on ordinary module tables. **No audit table exists yet**, so nothing is append-only in this PID; that arrives with `GEN-009`.
- Dev compose, CI database step, `.env.example` and `modules/platform` connection handling create and use the two roles from the start. The app connects as `pemo_app`, migrations as `pemo_owner`.
- **The grant-completeness check** in `--check`: every table in the seven schemas carries `pemo_app`'s expected grants; a table missing one fails loudly, naming it.

**The obligation and its guard ship together.** A migration that adds a table and forgets the grant is a runtime failure on deploy, in a module unrelated to whoever wrote the migration. That is the rot this model is most prone to, so the check is not a follow-up.

## Done when

Each proven by making it fail.

1. **`pemo_app` is not a superuser** — `rolsuper = false` — and does not own the tables (`pemo_owner` does). Show both.
2. **Restriction now binds where it could not before** — revoke `UPDATE` from `pemo_app` on one table and show the `UPDATE` refused, where the same operation as the old superuser `pemo_dev` succeeded. The property `GEN-009` depends on, in miniature. Restore afterwards.
3. **The app still does its work** — migrate, seed, run as `pemo_app`: the full suite reaches its green (166/0, 105/0, differential, boundaries), so least-privilege took away nothing the app legitimately needs.
4. **The grant-completeness check fires** — remove a grant from one table, `--check` fails loudly naming it; restore, it passes; and it does not false-warn on a complete table.

## Boundary

**Repository role model only.** Applying these roles to any out-of-repo production environment is explicitly **not** in scope — the decision's live-rollout clause is separate, higher-risk, and contingent on a production being found to exist. Build for a world with no live estate, because that is the world the repository describes.
