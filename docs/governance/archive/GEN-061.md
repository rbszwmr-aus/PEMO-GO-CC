# GEN-061 — a local Flutter run is gated to the version the workflow pins

Surfaced resolving the GEN-056 version contradiction. The PO relayed `flutter --version` = 3.44.3;
this host reports 3.44.9, and `which -a flutter` returns nothing — Flutter is reachable here ONLY by an
explicit path, never PATH. So a bare `flutter test` locally does not identify what ran, and my GEN-056
suite ran one patch above the gate (3.44.9 vs the pinned 3.44.3).

**Why this is a gate, not a nicety.** We have spent a day this week on local-vs-CI divergences (the
reporter format, the missing origin/main, the boundary scanner) — each a gate that saw what CI did not,
because it ran something CI did not. A one-patch toolchain gap reintroduces exactly that class, cheaply
and invisibly. And GEN-056 exists *because* of version drift between a contract and its generated
consumers; running the tool that regenerates them on a different SDK than the gate is that same mistake
in another hat. A local run one patch ahead is a fast guess; the point of installing Flutter was to
make it a gate.

## What landed

- **3.44.3 installed ALONGSIDE 3.44.9** (not replacing it): `~/tools/flutter-3.44.3`, cloned from the
  existing SDK's git repo at the `3.44.3` tag and bootstrapped — `Flutter 3.44.3 • engine e1fd963c6f •
  Dart 3.12.2`, matching the pin's toolchain exactly.
- **`apps/resident-mobile/tool/flutter-pinned.sh`** — the local runner. It DERIVES the pin by reading
  `.github/workflows/governance.yml`'s `flutter-version` (never typed here, so it cannot drift from the
  gate), resolves the SDK EXPLICITLY (`~/tools/flutter-<pin>`, or `PEMO_FLUTTER_SDK`), and — because a
  directory name is not proof of a version — asks the binary and REFUSES if its reported version is not
  the pin. The workflow is untouched: the CI pin stays the source of truth and the runner follows it.

## Bite (`run-mutations GEN-061`, kind guard, 1 proven)

Point the runner at a hermetic fake SDK reporting `Flutter 9.9.9` → it refuses, naming both the
resolved version and the pin ("a local run on the wrong version is a guess, not a gate"). The fake SDK
is built in the bite itself, so it needs no second real install and bites the same in CI. `expect` is
pin-independent, so a legitimate pin bump does not silently pass the bite. Proven separately by hand
against the real 3.44.9 install: refuses naming 3.44.3.

## Verification on the pin

With the runner resolving 3.44.3, the GEN-056 resident-mobile suite is **280 tests, all pass** — so
GEN-056's local claim is upgraded from "green on 3.44.9" to "green on the gate's 3.44.3".

## Principle
