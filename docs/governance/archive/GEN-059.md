# GEN-059 — the cross-schema SQL scanner matches text, not SQL (UI-054 G-finding)

Main went red at `9063278` (UI-054's merge) on the `no-cross-schema-sql` boundary check:

```
FAIL  no-cross-schema-sql(apps/management-web/tool/live-exercise.ts) — notices.length
```

There is no SQL in that file; it makes HTTP calls. `apps/management-web/tool/live-exercise.ts:184`:

```js
say(`${who}: ${l.data.notices.length} notices visible, ${mine.length} from this run`);
```

The scanner extracts string literals carrying a SQL verb and matches `\b<schema>\.<ident>`
against them. This template literal (a) carries the English word **"from"** (a SQL verb by the
word test) and (b) interpolates `${l.data.notices.length}`, whose text `notices.length` matches
the `notices` **schema** name. A printed log line is read as a cross-schema SQL statement.
Any scanned file printing `.notices.`, `.resident.`, `.property.` etc. trips it.

UI-054 landed a one-line binding as a labelled WORKAROUND so main goes green; the real fix is here.

## Rulings (from the incident)

- **D1** — the scanner requires SQL CONTEXT, not a bare schema-qualified name. State the rule and why it is not merely a bigger denylist.
- **D2** — template-literal INTERPOLATION TEXT is not string content to read as SQL. Decide and state whether interpolations are excluded entirely or only when no SQL verb is present.
- **D3** — bites BOTH ways: a real cross-schema SQL string still reds (plant one), AND a printed `x.notices.length` no longer reds (UI-054's exact line as a fixture).
- **D4** — re-run the scanner over the whole repo; report how many other false positives it was silently carrying.
- Principle to register: `a-guard-that-matches-text-without-its-context-reds-for-someone-elses-reason`.
