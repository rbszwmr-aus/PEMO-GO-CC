# GEN-057 — the integration suite must be deterministic (GEN-048 F7)

Ahead of GEN-055 (C3) and GEN-056 (regeneration) — **both hold until this lands**. The same commit
`9abfabb` was GREEN on `codex/gen-048` (#103) and RED on `main` (#104): an unstable suite certifies
nothing, green or red. Cause: 61 integration files share ONE database, and a teardown reaches outside
its own fixtures (`membership-assertions.test.ts` deletes `user_group LIKE 'grp_w3%'`, which matches
another file's `grp_w3r_one`), so the verdict depends on glob file order.

- **D1 DIAGNOSE AND STATE** the actual concurrency and the actual isolation — measured. (Opening
  measurement: 61 files, 32 touch the DB, one database, run `--test-concurrency=1`.)
- **D2 ISOLATE:** per-file schema/database, or serialise, chosen by measured runtime cost and stated.
  Isolation preferred; serialisation acceptable if stated as the cost of correctness.
- **D3 TEARDOWN OWNS ONLY WHAT IT CREATED:** sweep every integration file; a teardown deletes only rows
  its own setup inserted, never a seeded or foreign fixture. Bite: point a teardown at a foreign
  fixture → red naming the file and the row.
- **D4 PROVE DETERMINISM:** run the whole integration suite N ≥ 10 times under the chosen isolation,
  including ≥ 1 shuffled file order; report N/N identical. Register
  `a-suite-whose-verdict-depends-on-file-order-certifies-nothing`.
- **D5** re-run main; GEN-048 closes on THAT green run's URL plus the browser line.

Report: the diagnosed concurrency/isolation, the sweep's file count, the N/N result, and how many
teardowns were reaching outside their own fixtures — that number is the real size of the class.
