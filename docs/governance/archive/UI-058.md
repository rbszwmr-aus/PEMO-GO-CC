# UI-058 — Hotfix: unblock main's boundary guard on live-exercise.ts (a workaround, not a fix)

## What to build

A one-file hotfix. `UI-054`'s merge turned `main` red: apps/api's `verify:boundaries`
(the `no-cross-schema-sql` scanner, in the CI step "module boundaries hold, including
the composition layer") reported one violation —

```
FAIL  no-cross-schema-sql(apps/management-web/tool/live-exercise.ts) — notices.length
```

**This is the guard doing its job on a false positive, not a defect in the code.** The
scanner extracts string literals and matches `\b<schema>\.<ident>`; `notices` is both
this contract's list field (`StaffNoticeListResponse.notices`) and a database schema
name, so the text `notices.length` inside a template-literal interpolation
(`${l.data.notices.length}`) was read as a cross-schema SQL reference — with no SQL and
no SQL verb anywhere near it.

The change binds `l.data.notices` to a local so that text does not appear inside a
string literal. **It is a WORKAROUND, said so on the line, in this PID, and in the
report.** We do not silently rename around guards: a codebase that learns "the guard
complained, so change the name" loses the guard. The binding stays only until Main CC's
scanner-precision PID lands (gate on an actual SQL verb; do not scan interpolated
expression text); after that the binding may remain — it reads fine — but the comment
goes.

Also owed by this PID, as a report item only (not fixed here): the list of which checks
the UI pre-push gate runs versus which the CI `register` job runs. The
`no-cross-schema-sql` class is invisible to the UI track locally, the third time a local
gate has seen less than CI. The list is what the next governance PID acts on.
