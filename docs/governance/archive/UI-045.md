# UI-045 — Notices staff screens, part 1: reads against management-web 2.0.0

## What to build

Three read-only staff screens over the notices reads the contract froze at `2.0.0`
(`GEN-043` reshaped `listNotices` and `getNotice` to the `ADR-019` model; `GEN-042`
added `getNoticeOutstanding`), plus a top-level **Notices** entry in the existing
flat sidebar. The surface derives from `ADR-019` and the contract, **not** from
`requirements/10` — only that document's `A-05` approval-queue *behaviours*
(list-left / detail-right, oldest-first, `J`/`K` keyboard traversal) carry over.

- **N1 Notices list** — `listNotices`. Type, title, lifecycle state, publish/expire,
  mandatory-ack. Filter by state and by type. `ADR-007`'s twist rule permits this:
  the server has already decided *which* notices this caller may see (read is
  inclusive — targeting intersecting scope, drafts included), and narrowing an
  already-authorized list is presentation. The client reasons about no role and no
  scope, and the filter asserts nothing about completeness.
- **N2 Notice detail** — `getNotice`. The current assertion in **both** languages
  (`ADR-019` `OQ3`: per-language fields on one assertion), lifecycle state, targeting
  rule in its staff-visible shape, response options when declared, and the
  disposition history — which `ADR-019` `D4` makes *the* answer to "what happened to
  this notice", because state is computed from the chain and never stored. A draft's
  detail **is** the COM-05 preview and is labelled so.
- **N3 Outstanding acknowledgements** — `getNoticeOutstanding`. Per-recipient
  read / acknowledged / response for one notice, counts computed from that payload
  and from no second call.

**No lifecycle control is rendered — not one, not even disabled.** The eighteen write
operations exist in `2.0.0` and the client cannot tell who may invoke them: it has no
role concept and, per `UI-004`'s overview ruling, must not acquire one. A control the
viewer may not use is a lie about their authority, and a disabled one asserts the
capability exists. The honest signal is the server's permitted actions, arriving with
`2.1.0` in part 2. Until then the deferred acts are **named as absent**, the treatment
`UI-019` established.

**Vocabularies are read from the contract, never hand-listed.** `lifecycleState` and
`disposition` are deliberately disjoint enums so that comparing against the wrong one
is a type error rather than a silent false; a hand-copied list would reintroduce
exactly the silent false the disjointness buys. `UI-024`'s rule applies: derive the
values, not the binding.

## Done when

1. **Three screens × four states × two locales = 24 cells**, each asserted, and each
   proven to fail **for its own reason** by mutation — a cell that goes red because the
   page broke is not covered. Shown for one state per screen.
2. **Every rendered claim about the data has a data-claim register entry**; a mutation
   that renders an unregistered claim reds.
3. **List and detail render byte-faithfully from the frozen fixtures**
   (`mob-s5-notices/list.json`, `detail.json`, `lifecycle.json`); a mutation altering a
   fixture-bound value reds. **N3 has no fixture** — see the gap below.
4. **Bilingual:** both languages present in detail with a working toggle; the existing
   client-copy scan reds on a hard-coded user-visible string.
5. **No controls:** a test asserts no lifecycle action element exists anywhere in part 1,
   so part 2 must consciously add them behind permitted actions.
6. **No role or scope reasoning on the client:** a test proves no code path branches on
   a role name.
7. **Nav entry present; URL-as-state round-trips** for all three screens.
8. Full management-web suite green locally, counts reported (node + Playwright);
   `F2` comments and the `F5` divergence footer cleaned; `UI-004` read in full, its
   still-valid findings carried, and close-as-superseded proposed with a one-paragraph
   summary for the PO to rule on.

**Named gap, carried from the readout and verified before this PID was filed:**
`getNoticeOutstanding` **has no fixture in the frozen corpus** — `GEN-042`'s own report
records "No fixtures were added for the new operations", `GEN-043` repeats it, and no
management-web fixture carries a `residentId`. N3 therefore renders as a **stated gap**
with its bilingual reason, the treatment the five existing `no-fixture` cells already
use. Inventing recipient acknowledgement data to fill it is forbidden. The fixture is a
finding for the backend track.
