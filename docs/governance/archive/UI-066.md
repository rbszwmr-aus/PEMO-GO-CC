# UI-066 — The corpus digest hashes what is authored, not what is stamped

## Number

`--next` returned `063`, but `063` (GEN-063) and `064` (GEN-064) are allocated on
`codex/gen-063` / `codex/gen-064` and `065` is reserved for UI-065 — none landed on
main's register yet, so `--next` cannot see them. Taking `063` would collide and
reissue a number another track holds (rule 1: never reissued). This PID takes the
lowest number free across all known allocations: **066**. The 063–065 gap on main is
those unlanded/reserved allocations, not an orphan.

## What to build

Per `RULING-corpus-digest-hashes-authored-not-stamped-2026-09-06.md` (decision (b)),
and the registered principle **`a-digest-must-hash-what-is-authored-not-what-is-stamped`**.

`corpus-digest.json` hashes each fixture's bytes, which include the `contractVersion`
that `packages/api-contracts/stamp-version.mjs` **stamps** in from `openapi.yaml`'s
`info.version`. UI CC neither writes nor owns that field. So a backend contract bump
(GEN-064's 2.2.0→2.3.0) reds `CorpusGuardError` with ~29 diffs that are pure
version-stamp noise — a false alarm indistinguishable from a real one, recurring on
every future bump.

- **The fix, in `corpus-source.ts`:** the corpus digest **excludes the stamped
  `contractVersion`** (the only field `stamp-version` writes into a fixture) from its
  hash. Neutralise it before hashing, mirroring `stamp-version`'s own targeted byte
  substitution (`/("contractVersion": ")[^"]*(")/`) — never a JSON round-trip, which
  would renormalise hand-authored bilingual copy. One change in the shared `sha256`
  path, so record and check stay identical. A contract version bump must never, by
  itself, trip the corpus guard.
- **Re-record the digest ONCE** under the corrected (version-independent) rule, and
  **verify the screens render** — this is the guard's own instruction honoured (not the
  blind re-record decision (a) refused), because the corpus content is unchanged: only
  what the digest hashes changed.
- **Not** on `codex/gen-064`. **Lands on main first**; GEN-064 then rebases and its
  stamp no longer reds the guard.

The `counts` and `getOverview` corpus GEN-064 adds are **not** in scope (§4 of the
ruling): their digest certification is deferred to the UI track that renders them, if
contract-parity requires it at all. This PID touches only the version-stamp coupling.

## Done when

1. A version bump alone leaves every digest unchanged — proven by a guard that also
   proves an authored-content change still moves the digest, and that `stamp-version`
   stamps no fixture field beyond `contractVersion` (so "any other stamped field" is
   caught structurally, not enumerated).
2. Digest re-recorded once; the management-web suite is green from a clean clone.
3. Carried: the two readouts as D0; the UI-058 closed-date corrected to UTC.

## Close note — the two-copy question (UI-066-RULINGS)

`stripStampedVersion` carries its OWN copy of stamp-version's substitution regex
(`/("contractVersion": ")[^"]*(")/`). Which branch of the ruling applies: **the
uncaught one.** Test 1 (`a contract-version bump alone leaves the digest unchanged`)
uses a HAND-EDITED version string with its own regex, not the real `stamp-version`
tool; test 3 catches only a NEW stamped field name, not a FORMAT divergence between the
two copies of the contractVersion regex. So the drift is currently uncaught
(`a-consumer-outside-the-stamp-check-is-not-a-consumer-it-is-a-copy`).

**Rides the next UI PID's first commit, NOT a reopen of UI-066:** either the round-trip —
drive the real `stamp-version` over a fixture, assert `stripStampedVersion` neutralises
exactly what it wrote — or bind both to one shared pattern.
